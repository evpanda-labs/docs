OCPI is symmetric: you are a server to your roaming partners and a client to them, often within the same request. EVPanda records both sides, and the direction is never something you pass — it follows from the method you call.

## The two directions

| You call | Direction | You are the… | Typical case |
| --- | --- | --- | --- |
| `captureInboundMessage` | `IN` | server | An eMSP pushes a CDR or session update to your endpoint |
| `captureOutboundMessage` | `OUT` | client | You pull a partner's locations, or post a token authorization |

Both take the same input: an identity and the HTTP exchange. There is no `direction` field to get backwards.

<Warning>
  In **both** directions, identity is the **partner on the other side of the exchange** — never your own platform. When Acme pushes you a CDR, the identity is Acme. When you pull Acme's locations, the identity is still Acme.
</Warning>

## Resolving partner identity

Your OCPI server already knows who is calling: you looked the partner up by their Token A or Token B to decide whether to serve the request at all. That lookup is your identity source.

```mermaid
flowchart LR
    A["Partner request"] --> B["Your auth layer<br/>token → partner"]
    B --> C["Capture adapter<br/>reads the resolved partner"]
    C --> D["Your OCPI handler"]
```

The order matters. Adapters resolve identity once per request, so they must run **after** whatever authenticates the partner. Mounted the other way around, no request has an identity yet, every message fails validation, and you see nothing in the dashboard.

<Note>
  A request with no resolvable identity is served exactly as it would have been — the adapters never block, alter, or fail a request on EVPanda's account. They simply don't capture it.
</Note>

## Adapters

Adapters assemble the exchange for you: collect headers and bodies, resolve the partner, and call the right capture method. What ships today:

| SDK | Inbound (you are the server) | Outbound (you are the client) |
| --- | --- | --- |
| **Go** | `ocpi.Middleware` — standard `func(http.Handler) http.Handler` | `ocpi.RoundTripper` — wraps any `http.RoundTripper` |
| **Node** | `ocpi.express` — connect-style `(req, res, next)` | `ocpi.fetch`, `ocpi.axios` |
| **Python** | *Not yet* — call the capture methods directly | *Not yet* — call the capture methods directly |

Because the Go middleware is the stdlib shape, it drops into net/http, chi, and gorilla/mux directly, and into echo and gin through their stdlib wrappers. The Node express adapter is typed against `node:http`, so it works on connect too, with no express dependency.

For anything else — koa, hono, fastify, FastAPI, Django — skip the adapter and call the capture methods yourself. It is a few lines, and you hand the identity over directly instead of resolving it.

## How identity reaches an adapter

Each SDK ships a default resolver and lets you replace it.

<Tabs>
  <Tab title="Go">
    The default resolver reads the request **context** first, then falls back to `X-EVPanda-*` headers. Stamp the context wherever you already look the partner up:

    ```go
    ctx := ocpi.ContextWithIdentity(r.Context(), evpanda.RoamingIdentity{
        PlatformID:   partner.ID,
        PlatformName: partner.Name,
    })
    next.ServeHTTP(w, r.WithContext(ctx))
    ```

    If identity lives somewhere else entirely — a client certificate, a path prefix — pass your own resolver with `ocpi.WithResolver`.
  </Tab>

  <Tab title="Node">
    Adapters take a `resolve` callback that receives the request's method, URL, and headers, and returns a `RoamingIdentity`:

    ```ts
    const resolve = ({ requestHeaders }) => {
      const partner = lookupPartner(requestHeaders.authorization);
      return {
        platformId: partner?.id ?? "",
        platformName: partner?.name ?? "",
      };
    };

    app.use(ocpi.express(panda, { resolve }));
    ```

    Omit `resolve` and the shipped default reads the `X-EVPanda-*` headers, which earlier middleware must stamp.
  </Tab>

  <Tab title="Python">
    There are no adapters yet, so there is no resolver — you pass the identity to the capture call directly:

    ```python
    panda.capture_inbound_message(
        OCPIMessageInput(identity=identity, data=exchange)
    )
    ```
  </Tab>
</Tabs>

### The `X-EVPanda-*` headers

Every SDK's default resolver understands the same four headers, matched case-insensitively:

| Header | Field | Required |
| --- | --- | --- |
| `X-EVPanda-Platform-Id` | `platformId` | Yes |
| `X-EVPanda-Platform-Name` | `platformName` | Yes |
| `X-EVPanda-Tenant-Id` | `tenantId` | Optional pair |
| `X-EVPanda-Tenant-Name` | `tenantName` | Optional pair |

They exist so a host can stamp identity in middleware it already has, without writing a resolver. Partners never send them, and never receive them: the outbound adapters strip all four before dispatch, so your tenant names stay internal.

<Tip>
  Prefer the context (Go) or a `resolve` callback (Node) over headers. Both keep identity out of the HTTP layer entirely, and neither can be spoofed by a partner who guessed the header names.
</Tip>

## What gets captured

For each exchange: the method, the URL, the response status, the request and response bodies, and the headers that survive the [allowlist](/concepts/data-handling#ocpi-the-header-allowlist). `Authorization` never makes it into the buffer, and tokens in `/credentials` bodies are masked.

Bodies are read as your application reads them, not buffered up front:

- **Inbound**, the request body is recorded as your handler consumes it. A handler that ignores the body records none — streaming handlers are never forced into memory.
- **Outbound**, capture completes when you close the response body, which you have to do anyway. A response you never read is never shipped.

## Common mistakes

<AccordionGroup>
  <Accordion title="Mounting the adapter before your auth layer" icon="arrow-up-down">
    This is the single most common integration fault. The adapter runs, finds no identity, and skips capture — on every request. `DroppedInvalid` climbs, nothing arrives, and the requests themselves work perfectly, so nothing looks broken. Mount capture *after* auth.
  </Accordion>

  <Accordion title="Capturing only inbound traffic" icon="arrow-down">
    Half of OCPI is the calls you make. Without them, you can see a partner's failures but never your own, and EVPanda can't tell you which side of a failed roaming session broke.
  </Accordion>

  <Accordion title="Sending your own platform as the identity" icon="user-x">
    Then every message in the network is attributed to you, and per-partner error rates become meaningless. Identity is always the other side.
  </Accordion>

  <Accordion title="Forgetting a body parser (Node)" icon="file-x">
    The express adapter reads the request body from `req.body`, so a body parser must be mounted first. Without one, exchanges are captured with no request body at all.
  </Accordion>

  <Accordion title="Wrapping fetch but calling axios" icon="shuffle">
    In Node, axios goes through `node:http`, never `fetch`. Wrapping one captures nothing from the other — instrument whichever client your OCPI calls actually use.
  </Accordion>
</AccordionGroup>
