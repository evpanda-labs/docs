title: "Quickstart"
description: "Create a network, install the SDK, and send your first captured message to EVPanda."
---

This guide takes you from an empty EVPanda account to live traffic in the dashboard. It should take about ten minutes.

## Prerequisites

- An EVPanda account. If you don't have one, [get in touch](mailto:support@evpanda.io).
- A service to instrument: an OCPP 1.6 CSMS, an OCPI 2.2.1 server, or both.
- Go 1.24+, Node 18+, or Python 3.12+.

<Steps>
  <Step title="Create a network">
    A network is the container for everything EVPanda records for one of your systems. Networks come in two kinds, and you create one per protocol you want to observe.

    1. Sign in to [app.evpanda.io](https://app.evpanda.io).
    2. Create a **Charger network** for an OCPP CSMS, or a **Roaming network** for an OCPI server.
    3. Give it a name that matches the system it watches, such as `Production CSMS`.

    <Tip>
      Create one network per environment. Keeping staging traffic out of your production network keeps issue counts meaningful.
    </Tip>

    See [Networks and API keys](/concepts/networks) for how networks map to your infrastructure.
  </Step>

  <Step title="Generate an API key">
    Open your network's **Settings** tab and generate an API key. The raw key is shown **once** — copy it immediately and store it in your secret manager.

    Keys look like `evp_sk_…` and are scoped to a single network, so an OCPP key cannot write OCPI traffic or reach any other network.

    Export it where your service runs:

    ```bash
    export EVPANDA_API_KEY="evp_sk_..."
    ```

    Every SDK reads `EVPANDA_API_KEY` from the environment when you don't pass a key in code.
  </Step>

  <Step title="Install the SDK">
    <CodeGroup>
      ```bash Go
      go get github.com/evpanda-labs/evpanda-go
      ```

      ```bash Node
      npm add @evpanda/sdk
      ```

      ```bash Python
      pip install "evpanda[zstd]"
      ```
    </CodeGroup>

    <Note>
      **Package availability.** The Go SDK is published. The Node package on npm is behind the API documented here — install `@evpanda/sdk@0.1.0` or later once it is published. The Python SDK is in preview; until it reaches PyPI, install it from source: `pip install "git+https://github.com/evpanda-labs/evpanda-py"`.
    </Note>
  </Step>

  <Step title="Start a client">
    The protocol is the client. `OCPI` and `OCPP` have separate client types, separate configs, and separate API keys — pick the one your service speaks. Starting a client launches one background worker that owns delivery.

    <CodeGroup>
      ```go Go
      import evpanda "github.com/evpanda-labs/evpanda-go"

      // APIKey omitted → read from EVPANDA_API_KEY.
      panda, err := evpanda.StartOCPP(evpanda.OCPPConfig{
          BaseConfig: evpanda.BaseConfig{Endpoint: "https://ingest.evpanda.io"},
      })
      if err != nil {
          log.Printf("evpanda: %v (running inert)", err)
      }
      defer func() { _ = panda.Close() }()
      ```

      ```ts Node
      import { OCPPClient } from "@evpanda/sdk";

      // apiKey omitted → read from EVPANDA_API_KEY.
      const panda = OCPPClient.start({
        endpoint: "https://ingest.evpanda.io",
      });

      process.on("SIGTERM", () => void panda.close());
      ```

      ```python Python
      from evpanda import OCPPClient, OCPPConfig

      # api_key omitted → read from EVPANDA_API_KEY.
      panda = OCPPClient.start(
          OCPPConfig(endpoint="https://ingest.evpanda.io")
      )
      ```
    </CodeGroup>

    Start the client once, at boot, and share it across your process. It is safe for concurrent use.

    <Warning>
      A bad endpoint or a missing API key never crashes your service. The client comes back inert — every capture is a no-op — and the error tells you why. Log that error, or a typo will look like an idle system.
    </Warning>
  </Step>

  <Step title="Capture traffic">
    <Tabs>
      <Tab title="OCPP">
        Open a session when a charge point connects, record each frame, and close it when the socket goes away. The session mints the connection ID that ties the whole WebSocket lifetime together.

        <CodeGroup>
          ```go Go
          conn := upgrade(w, r)
          sess := panda.Connection(evpanda.ChargerIdentity{ChargerID: "CP-001"})
          defer sess.Disconnect()

          for {
              frame, err := conn.Read()
              if err != nil {
                  return
              }
              sess.Message(frame, evpanda.FromCP)

              reply := handleFrame(frame) // your CSMS logic
              conn.Write(reply)
              sess.Message(reply, evpanda.ToCP)
          }
          ```

          ```ts Node
          wss.on("connection", (socket, req) => {
            const session = panda.connection({ chargerId: "CP-001" });

            socket.on("message", (raw) => {
              const frame = raw.toString();
              session.message(frame, "FROM_CP");

              const reply = handleFrame(frame); // your CSMS logic
              socket.send(reply);
              session.message(reply, "TO_CP");
            });

            socket.on("close", () => session.disconnect());
          });
          ```

          ```python Python
          from evpanda import ChargerIdentity, OCPPDirection

          with panda.connection(ChargerIdentity(charger_id="CP-001")) as session:
              async for frame in socket:
                  session.message(frame, OCPPDirection.FROM_CP)

                  reply = handle_frame(frame)  # your CSMS logic
                  await socket.send(reply)
                  session.message(reply, OCPPDirection.TO_CP)
          ```
        </CodeGroup>

        `FROM_CP` is a frame the charge point sent you; `TO_CP` is one you sent it. Replace the hard-coded `CP-001` with however your CSMS already identifies a charge point at handshake — see [Instrument an OCPP CSMS](/ocpp/overview).
      </Tab>

      <Tab title="OCPI">
        OCPI traffic flows in both directions, and the method name sets the direction. Use the HTTP adapters where your framework has one; they assemble the exchange for you.

        <CodeGroup>
          ```go Go
          import "github.com/evpanda-labs/evpanda-go/ocpi"

          // Inbound: partners calling your OCPI server.
          srv := &http.Server{Handler: auth(ocpi.Middleware(panda)(mux))}

          // Outbound: your calls to partners.
          client := &http.Client{Transport: ocpi.RoundTripper(panda, nil)}
          ```

          ```ts Node
          import { ocpi } from "@evpanda/sdk";

          // Inbound: partners calling your OCPI server.
          app.use(express.json());
          app.use(ocpi.express(panda, { resolve: resolvePartner }));

          // Outbound: your calls to partners.
          const fetch = ocpi.fetch(panda, globalThis.fetch, {
            resolve: resolvePartner,
          });
          ```

          ```python Python
          from evpanda import HttpExchange, OCPIMessageInput, RoamingIdentity

          # No adapters yet — call the capture methods directly.
          panda.capture_inbound_message(
              OCPIMessageInput(
                  identity=RoamingIdentity(
                      platform_id="acme", platform_name="Acme Mobility"
                  ),
                  data=HttpExchange(
                      method="POST",
                      url="/ocpi/2.2/cdrs",
                      status_code=201,
                      request_headers={"content-type": "application/json"},
                      request_body=body,
                  ),
              )
          )
          ```
        </CodeGroup>

        Every OCPI message must carry the identity of the **partner on the other side** — never your own platform. See [Instrument an OCPI server](/ocpi/overview) for how to resolve it from your auth layer.
      </Tab>
    </Tabs>
  </Step>

  <Step title="Verify it works">
    Drive some traffic through your service, wait for a flush — at most five seconds by default — and open your network in the dashboard. Messages appear under **Messages**, and chargers or platforms are discovered automatically as they send traffic.

    If nothing shows up, ask the SDK. In Go, every client exposes counters that each map to one root cause:

    ```go
    s := panda.Stats()
    log.Printf("captured=%d invalid=%d oversize=%d evicted=%d undeliverable=%d",
        s.Captured, s.DroppedInvalid, s.DroppedOversize,
        s.DroppedEvicted, s.DroppedUndeliverable)
    ```

    `Captured: 0` means the capture calls aren't running at all. A high `DroppedInvalid` means identity resolution is failing. In Node and Python, turn on `debug` to get the same picture in your logs.

    Work through [Troubleshooting](/operate/troubleshooting) for the rest.
  </Step>

  <Step title="Shut down cleanly">
    Stop accepting traffic first, then drain what the SDK still holds. Closing without draining discards whatever hasn't shipped yet.

    <CodeGroup>
      ```go Go
      srv.Shutdown(ctx)               // stop accepting…
      if err := panda.Shutdown(ctx); err != nil {
          log.Printf("evpanda: %v", err) // …then drain
      }
      ```

      ```ts Node
      await server.close();
      await panda.close();
      ```

      ```python Python
      server.shutdown()
      panda.close()
      ```
    </CodeGroup>
  </Step>
</Steps>
