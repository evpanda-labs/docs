## Install

```bash
go get github.com/evpanda-labs/evpanda-go
```

Requires Go 1.24 or later. The SDK has one dependency — `klauspost/compress`, for zstd.

## Start the client

Start one client at boot and share it. `StartOCPP` always returns a usable client: if the config is bad you get an inert one plus an error, so a typo in your environment can't stop your CSMS from booting.

```go main.go
package main

import (
	"log"
	"net/http"

	evpanda "github.com/evpanda-labs/evpanda-go"
)

func main() {
	// APIKey omitted → read from the EVPANDA_API_KEY environment variable.
	panda, err := evpanda.StartOCPP(evpanda.OCPPConfig{
		BaseConfig: evpanda.BaseConfig{
			Endpoint: "https://ingest.evpanda.io",
		},
	})
	if err != nil {
		log.Printf("evpanda: %v (running inert)", err)
	}
	defer func() { _ = panda.Close() }()

	csms := &CSMS{panda: panda}
	http.HandleFunc("/ocpp/", csms.HandleWebSocket)
	log.Fatal(http.ListenAndServe(":8080", nil))
}
```

<Warning>
  Log that error. An inert client behaves exactly like a healthy one on an idle system — silent, no panics, no failures — so a swallowed config error looks identical to "no chargers connected yet".
</Warning>

## Capture a connection

The example below uses [gorilla/websocket](https://github.com/gorilla/websocket), but nothing here is specific to it: swap in `nhooyr.io/websocket` or your own upgrader and the three capture calls stay in the same places.

```go csms.go
package main

import (
	"log"
	"net/http"
	"strings"

	evpanda "github.com/evpanda-labs/evpanda-go"
	"github.com/gorilla/websocket"
)

var upgrader = websocket.Upgrader{
	Subprotocols: []string{"ocpp1.6"},
}

type CSMS struct {
	panda *evpanda.OCPPClient
}

func (c *CSMS) HandleWebSocket(w http.ResponseWriter, r *http.Request) {
	// 1. Identify the charge point exactly as your CSMS already does.
	identity, ok := resolveCharger(r)
	if !ok {
		http.Error(w, "unknown charge point", http.StatusUnauthorized)
		return
	}

	conn, err := upgrader.Upgrade(w, r, nil)
	if err != nil {
		return // the upgrader already wrote the error response
	}
	defer conn.Close()

	// 2. Open the capture session. This records the connect and mints the
	//    connection ID that ties this socket's frames together.
	sess := c.panda.Connection(identity)
	defer sess.Disconnect()

	cp := &chargePoint{conn: conn, sess: sess}

	for {
		_, frame, err := conn.ReadMessage()
		if err != nil {
			return // socket closed — the deferred Disconnect records it
		}

		// 3. Capture before you handle, so a frame that breaks your
		//    handler is still recorded.
		sess.Message(frame, evpanda.FromCP)

		reply, err := c.handleFrame(identity, frame)
		if err != nil {
			log.Printf("csms: %v", err)
			continue
		}
		if err := cp.Send(reply); err != nil {
			return
		}
	}
}

// resolveCharger reads the charge point identity from the URL path:
// wss://csms.example/ocpp/CP-001. Use whatever your CSMS already relies
// on — Basic auth, a client certificate, or a database lookup.
func resolveCharger(r *http.Request) (evpanda.ChargerIdentity, bool) {
	id, ok := strings.CutPrefix(r.URL.Path, "/ocpp/")
	if !ok || id == "" {
		return evpanda.ChargerIdentity{}, false
	}
	return evpanda.ChargerIdentity{ChargerID: id}, true
}
```

## Capture outbound frames

A CSMS writes from more than one place — the read loop's replies, and calls your operators or schedulers initiate. Put the write and the capture behind one helper so nothing can reach the socket uncaptured, and so the write lock a WebSocket needs is held over both.

```go send.go
type chargePoint struct {
	conn *websocket.Conn
	sess *evpanda.OCPPSession

	mu sync.Mutex // gorilla allows one concurrent writer
}

// Send writes a frame to the charge point and captures it. Every outbound
// frame in the CSMS goes through here — replies from the read loop and
// CSMS-initiated calls alike.
func (cp *chargePoint) Send(frame []byte) error {
	cp.mu.Lock()
	defer cp.mu.Unlock()

	if err := cp.conn.WriteMessage(websocket.TextMessage, frame); err != nil {
		return err
	}
	cp.sess.Message(frame, evpanda.ToCP)
	return nil
}
```

<Tip>
  Capture *after* a successful write. A frame that failed to send never reached the charge point, and recording it as sent would make the validation engine hunt for a response that was never going to come.
</Tip>

## The flat primitives

`Connection` is built on three lower-level calls. Use them when a session handle doesn't fit — replaying an archive, or capturing from a component that only sees frames.

```go
connectionID := uuid.NewString() // any UUID; stable per socket, fresh per reconnect

panda.CaptureConnect(evpanda.OCPPMessageInput{
	Identity:     identity,
	ConnectionID: connectionID,
})

panda.CaptureMessage(evpanda.OCPPMessageInput{
	Identity:     identity,
	ConnectionID: connectionID,
	Data:         frame,
	Direction:    evpanda.FromCP,
})

panda.CaptureDisconnect(evpanda.OCPPMessageInput{
	Identity:     identity,
	ConnectionID: connectionID,
})
```

`CaptureMessage` requires both `Data` and `Direction` and drops the message if either is missing. Connect and disconnect ignore both.

## Multi-tenant CSMS

Add the tenant pair to the identity at handshake. It is optional but all-or-nothing — set both fields or neither.

```go
evpanda.ChargerIdentity{
	ChargerID:  "CP-001",
	TenantID:   "cpo-42",
	TenantName: "Acme Energy",
}
```

## Shut down cleanly

Stop accepting connections first, then drain. `Shutdown` uses your context's deadline; `Close` uses the configured `DrainTimeout`. Both are idempotent, and captures made after them are safe no-ops.

```go
ctx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
defer cancel()

srv.Shutdown(ctx)                  // stop accepting first…
if err := panda.Shutdown(ctx); err != nil {
	log.Printf("evpanda: %v", err) // …then drain what was captured
}
```

`Shutdown` returns `evpanda.ErrDrainIncomplete` if the deadline passed with messages still buffered.

## Check that it's working

Every client exposes counters. Each one maps to exactly one root cause, so a single log line usually ends the investigation.

```go
s := panda.Stats()
log.Printf("evpanda: captured=%d invalid=%d oversize=%d evicted=%d undeliverable=%d buffered=%d",
	s.Captured, s.DroppedInvalid, s.DroppedOversize,
	s.DroppedEvicted, s.DroppedUndeliverable, s.BufferedMessages)
```

Or wire them into your metrics:

```go
prometheus.MustRegister(prometheus.NewCounterFunc(
	prometheus.CounterOpts{Name: "evpanda_dropped_evicted_total"},
	func() float64 { return float64(panda.Stats().DroppedEvicted) },
))
```

See [Monitoring](/operate/monitoring) for what each counter means and what to alert on.
